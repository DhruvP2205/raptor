# Stage Spec: Pairwise Judging Mode

Status: **Design only. Not implemented. Not claimed.**
This bonus challenge is not attempted in the running platform. This
document exists so the decision to defer it is informed, and so the
estimator is validated before anyone builds around it. Nothing here
should be described as a feature until it is built and demonstrated.
If code and this doc disagree, update this doc first.

---

## 1. What it is

Instead of asking a judge for absolute scores, show them two projects
and ask which is better. A statistical model (Bradley-Terry) recovers a
global ranking from all the choices. It sidesteps cross-judge
calibration entirely, because no judge is ever asked for a number that
has to be compared with another judge's number.

This is the direct answer to the weakness found in
`NORMALIZATION.md` Section 5: per-judge z-scoring struggles when each
judge sees only a few projects. A comparison does not need a judge's
personal scale at all.

## 2. Scope

- An event-level judging mode: `SCORING` (today's behavior) or
  `PAIRWISE`. One mode per event; no mixing inside an event.
- A judge screen showing two projects side by side.
- An estimator that turns comparisons into strengths and a ranking.
- Feeding that ranking into the existing results, publish, correction
  and lock flow in place of a normalization run.
- Out of scope: hybrid events using both modes, adaptive pair selection
  that learns which pairs are most informative.

## 3. Data model

| Table | Fields | Notes |
|---|---|---|
| `PairwiseComparison` | id, eventId, judgeId, winnerSubmissionId, loserSubmissionId, createdAt, supersededById | A judge may reverse a choice; the old row is superseded, never deleted, mirroring how score revisions work |
| `PairwiseRun` | id, eventId, createdAt, comparisonCount, iterations, createdByUserId | A frozen snapshot, like a normalization run |
| `PairwiseResult` | runId, submissionId, strength, rank | One row per submission per run |

Uniqueness: a judge sees a given unordered pair at most once.

## 4. Pair selection

A judge is assigned a batch of approved submissions (Module 7's
existing assignment). Pairs are drawn **within that batch**, balanced so
each project appears about equally often. Cross-judge connectivity comes
from overlapping batches, so assignment for a pairwise event must
overlap deliberately. The organizer dashboard shows how connected the
comparison graph is, because a disconnected graph cannot be ranked
across its parts (the estimator tolerates it, Section 5, but the result
would be meaningless across components).

Judge screen: two project cards, choose one, undo the last choice, or
skip a pair. A skip records nothing. On a phone the two projects stack.

## 5. The estimator

Bradley-Terry by the standard iterative minorization-maximization
update, with a **virtual reference project**: every project gets one
pseudo-win and one pseudo-loss against it. That keeps a project with no
losses finite and lets a disconnected graph still produce a total order.
Strengths are rescaled to a fixed geometric mean each pass.

A reference implementation and its tests are in
`scripts/bradley-terry-reference.py` (output in
`docs/bradley-terry-reference-output.txt`). It was run on 40 projects
with balanced random pairs and judge choices generated from the model:

| Comparisons per project | Total pairs | Rank recovery (Spearman) | Iterations |
|---|---|---|---|
| 3 | 59 | 0.556 | 122 |
| 5 | 99 | 0.653 | 163 |
| 8 | 159 | 0.742 | 196 |
| 12 | 239 | 0.804 | 211 |
| 20 | 399 | 0.872 | 211 |

Sanity check: with two disconnected pairs and an undefeated project,
all strengths stay finite.

**What this says about cost.** Accuracy climbs slowly: roughly eight
comparisons per project to reach 0.74, twelve for 0.80. For 40
projects and 30 judges, eight per project is about 160 pairs, or about
five pairs (ten project views) per judge. Scoring the same event needs
about four project views per judge. Pairwise is not cheaper for judges;
its argument is fairness, not effort. These accuracy figures come from
data generated by the model being fitted, so they are an optimistic
best case, not a forecast for real judges.

## 6. Integration with the existing pipeline

- The results draft selects a `PairwiseRun` exactly as it now selects a
  normalization run. Draft, publish, correction, versioning and the
  permanent lock at announcement are unchanged.
- Ties: strengths equal to six decimal places share a rank (dense
  ranking, as everywhere else).
- Role isolation is unchanged in principle: a judge reads only their own
  comparisons; another judge's are refused with 403, by the same guard
  pattern as the per-judge scores route.
- Exports: one new organizer export (comparisons and final strengths).
- Global Ranking, certificates, and voting consume ranks, not scores, so
  they need no change.

## 7. Honest cost estimate

This is the only bonus that is a second pipeline rather than a document
or a report: new tables and migration, new routes with guards, a new
judge screen (desktop and mobile), an estimator with tests, results
integration, an export, a demo dataset (the fixture has no comparisons,
so demonstrating it needs generated ones), and documentation. It should
be attempted only after everything else is settled.

## 8. What I'm testing for this module

- The estimator recovers a known ordering on generated data at the
  accuracy above, and stays finite on an undefeated project and on a
  disconnected graph.
- A judge cannot read or create comparisons for projects outside their
  assignment; another judge's comparisons return 403.
- Reversing a choice supersedes it and leaves history intact.
- A pairwise run locks at results announcement exactly as a
  normalization run does.
- A pairwise event and a scoring event, side by side, do not interfere.

## 9. Open questions

- How overlap between judge batches should be chosen so the graph is
  connected without inflating every judge's workload.
- Whether "skip" should be allowed unlimited times or capped.
