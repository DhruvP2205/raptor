# Frontend Design: Module 2 — Roles & Membership

Status: **Design locked, not yet implemented.**
References `DESIGN-SYSTEM.md` throughout — Button, Modal, Badge,
Textarea, Avatar components are used as specified there, not redefined.
Backend reference: `stages/02-roles-and-membership.md`.

---

## 1. Screens

1. **Admin: Create staff account** — form, two-step confirm.
2. **Admin/organizer: Judge invitation dashboard** — per-event list of
   invited judges with status, resend action.
3. **Judge: Accept/decline invitation** — the page an invite link opens.

---

## 2. Create staff account

### Structure
Fields: name, email, temporary password (generated by default, with a
"generate new" action — never left blank), role (`Judge` / `Organizer`
as two large radio-style options, not a dropdown — since this choice
is permanent per backend D10, it deserves more visual weight than a
select element gives it).

Submitting opens a **standard Modal** (`DESIGN-SYSTEM.md` 7.6), not the
destructive variant (this isn't reversible-with-consequence the way
disqualifying a submission is, but it *is* permanent, so it still gets
a real confirmation step, not an instant submit):
- Heading: "Create this Judge account?" (role-specific wording)
- Summary of what was entered (name, email, role) — a last look before
  it's irreversible.
- Confirm button: "Create account" (Button primary).

### States
| State | Behavior |
|---|---|
| Idle | Form empty, "Generate password" pre-fills a temp password |
| Validation error | Inline, per field (malformed email, empty name) |
| Confirm modal open | Form fields behind it are inert; Escape/Cancel returns to editable form unchanged |
| Submitting | Confirm button loading state |
| Success | Modal closes, toast: "Judge account created." Form resets. **The temp password is shown once more, in a copyable field, with a note: "Share these credentials directly — they won't be shown again."** This is the one moment credentials are visible; there's no "view password later" anywhere else in the product. |
| Error — email already in use | Inline error under the email field |
| Error — server/network | Standard reused error block |

### Flow
Enters from: an admin-only nav item (not visible to organizers or
judges — Module 2's account-type exclusivity means this screen simply
doesn't exist for them, not "exists but disabled"). Exits to: the
credentials-shown success state, then back to an empty form (this is
a repeatable action, likely used several times in a row when
onboarding many judges before an event).

## 3. Judge invitation dashboard

### Structure
Per-event screen (reached from the event's organizer view — see Module
3). A table: judge name/email, status Badge (`live`/pending amber,
`success`/accepted green, `neutral`/declined gray, `danger`/expired
red — mapping the four backend states onto the four semantic status
tokens), invited date, **Resend** action (visible only on
Pending/Declined/Expired rows, per backend rules).

Two ways to add a judge, both from a toolbar button:
- **Add existing judge** — search by name/email among accounts already
  `accountType: JUDGE`, select, sends an immediate invite (no separate
  confirm modal — inviting isn't itself irreversible the way disqualifying
  is; declining is always available to the judge afterward).
- **Generate joining link** — produces a copyable URL, explicitly
  labeled "Share this link with a judge — anyone who already has a
  judge account can use it to join this event."

### States
| State | Behavior |
|---|---|
| Empty (no judges invited yet) | Empty-state pattern (`DESIGN-SYSTEM.md` 7.12): "No judges invited yet." + the two add actions |
| Loaded | Table as above |
| Resend clicked | Button loading state → toast "Invitation resent." |
| Resend failed | Inline message next to that row, not a page-level error — one row's action failing shouldn't disrupt the rest of the table |
| Search (add existing judge) — no matches | "No judge accounts match that search." — **with no path to create one from here** — creating an account is the separate Section 2 screen, on purpose; this search only ever finds *existing* judge accounts |

## 4. Judge: Accept/decline invitation

### Structure
Reached via a direct link (email) or the shareable joining link
(Section 3). Shows: event name, event dates, a short line ("You've
been invited to judge this event") and two buttons: **Accept**
(primary) and **Decline** (secondary).

Declining opens a lightweight standard Modal — not destructive-styled
(declining isn't consequential to anyone but the judge's own
participation), but still a deliberate second step rather than an
instant action, since it's not reversible from the judge's side (they'd
need to be re-invited).

### States
| State | Behavior |
|---|---|
| Not logged in | Redirects to log in first (Module 1), with the invitation link preserved as the return path — matches the pattern already established for session-expiry redirects |
| Logged in, invitation valid | Accept/Decline as above |
| Accept clicked | Loading state → success: "You're judging **{event}**." + link into the event | 
| Decline clicked, confirmed | Success: "Invitation declined." — no further action needed, no dead-end message implying something's wrong |
| Invitation already responded to (accepted or declined elsewhere) | **Idempotent, matching backend behavior** — shows the same outcome state as if they'd just now taken that action, never an error. Someone clicking an old email link after already responding through the link shouldn't see a confusing error. |
| Invitation expired (past `eventStartsAt`, backend's live deadline) | "This invitation has expired." — no accept/decline actions, just a note that the event's judge invitations closed when the event started |
| Logged in as the wrong account (e.g. a participant account, not the invited judge) | Since account types are exclusive (backend Module 2), this can't actually happen for a real judge invite sent to a judge-type account — but if the link is opened by an unrelated logged-in account, the invitation clearly wasn't issued to them: "This invitation isn't for this account." No accept/decline shown |

## 5. Flow continuity check

- **Into this module:** from Module 1 (a fresh judge/organizer account's
  first login lands them at Set Password, *then* — for organizers —
  directly into the app; for judges, into a state with no events yet
  until they're invited to one via Section 4).
- **Out of this module:** accepting a judge invitation leads into the
  event (Module 3's event detail, judge view) — not yet written, but
  this is the exact hand-off point to note now while it's fresh.
  Creating a staff account (Section 2) has no further hand-off within
  this doc — the admin's next action is either creating another account
  or leaving this screen entirely.
- No orphaned screens: every screen here has both an entry point
  (nav item, email link, or joining link) and an exit (either into the
  app or back to a list), matching the discipline the events-list doc
  established.
